# codeindex — план разработки

Локальный индекс кода для ИИ-агентов: символы, рёбра вызовов, ссылки —
свой лексер + токенный сканер + свой резолвер имён, MCP-поверхность. Мотивация: repowise покрывает
health/историю/семантику, но не отвечает на структурные вопросы
(«кто вызывает функцию», «откуда пришло значение»); готовые решения
(Benzi) — проприетарные, бета, логин, Rust второго сорта.

## Принятые решения (2026-10-28; уточнено в тот же вечер)

- **Всё своё, на Rust, с нуля**: ни tree-sitter, ни stack-graphs, ни
  прочих парсинг-зависимостей. Свой лексер (src/lexer.rs) + токенный
  сканер элементов (src/lib.rs). Функционал НЕ режется — все фичи
  (рёбра вызовов, разрешение имён, MCP) остаются; меняется только
  реализация: своя, подконтрольная, расширяемая.
- v1: **только Rust**, хранилище **SQLite** (`.codeindex/index.db`,
  rusqlite bundled — единственная содержательная зависимость).
  Миграция хранилища на YantrikDB — после того как v1 приживётся.
- Честность рёбер: каждое ребро помечено
  `resolved | candidate | unresolved(причина)`. Не гадаем.
- Разрешение имён (M3) — СВОЙ резолвер: дерево модулей + разрешение
  use-путей + учёт impl/trait. До него — эвристика
  «имя + модульный путь» с пометкой candidate.
- Инкрементальность: SHA-256 содержимого файла; перепарсивать только
  изменившиеся.
- MCP-сервер (M4): stdio, инструменты `search_symbols`, `get_definition`,
  `get_callers`, `get_references`, `call_tree`, `blast_radius`, `stats`.

## Последствия решения «с нуля» (осознанные)

- Токенный сканер не видит раскрывшихся макросов — НО tree-sitter их
  тоже не раскрывал, так что паритета не потеряли.
- Разрешение имён делаем сами (M3): use-дерево + модульное дерево + учёт
  impl. Это самая трудная часть проекта и самое ценное ноу-хау.
- Лексер/сканер — наш код: любые фичи (док-комментарии к символам,
  span'ы, новые языки) добавляются без ожидания чужих релизов.

## Вехи

- **M0 (готово, переписан на свой лексер):** CLI `scan <path>` — walk +
  собственный lexer + токенный сканер: инвентарь
  fn/struct/enum/trait/impl/mod/union, 12/12 тестов (включая
  ловушки: fn-pointer в типах, keyword-after-dot, generics/where,
  impl-тип из `impl Trait for Type`). Само-сканирование
  yantrikdb-server: 148 файлов / 3899 символов. Зависимости: anyhow,
  clap (+tempfile dev).
- **M1 (готово):** SQLite-хранилище `.codeindex/index.db` — meta
  (schema_version), files(path, hash, mtime), symbols(file_id, name,
  kind, line); edges не создаются до M2/M3 — таблица, которую нечем
  честно заполнить, не нужна. Инкрементальный `index <path>`: ре-парс
  только по расхождению SHA-256 (mtime пишется, но решением не
  является), пути относительные, чужая schema_version → отказ.
  19/19 тестов; само-индексация: второй прогон 0 parsed, touch без
  правки не перепарсивает.
- **M2 (готово):** запросы по хранилищу + таблица edges с честным
  tier. Экстрактор мест вызовов: прямой вызов, метод, последний
  сегмент пути, турбофиш; определения (`fn/struct/enum/union Name(`)
  и ключевые слова исключены. CLI: `search` (подстрока,
  регистронезависимо), `definition` (точное имя, все совпадения —
  развяжет M3), `callers` (DISTINCT файл:строка + tier).
  Инкрементальность расширена meta `extractor_version`: смена
  экстрактора меняет производные данные без изменения файлов →
  один полный ре-парс. 26/26 тестов; живая проверка: `callers lex`
  = 6 настоящих мест вызова.
- **M3:** свой резолвер имён (модульное дерево + use-пути + impl/trait):
  resolved-рёбра вызовов Rust, `call_tree`, `blast_radius`.
- **M4:** MCP-сервер (stdio) с семью инструментами; документация
  подключения в zcode/opencode.
- **M5 (опционально):** бэкенд YantrikDB + эмбеддинги сигнатур для
  семантического поиска символов.

## Верификация (для каждой вехи)

- Юнит-тесты на фикстурах (маленькие .rs-файлы с известным содержимым).
- Мутационные проверки: сломать резолвер — тест обязан упасть.
- Само-сканирование: `codeindex scan .` и `index .` на собственном коде.
- Для M4: живой вызов инструментов MCP-клиентом (zcode) на этом репо.
